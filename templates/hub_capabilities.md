## Hub commands and what each one does

- **checkpoint** — Saves progress, commits, pushes — scoped to whichever project the session is in
- **resume / quick resume** — Pulls latest, checks compliance/tickets, picks up where left off. "quick resume" is the identical capability run in a faster mode right after a checkpoint, skipping sync checks — not a separate capability, just a lighter mode of this same one.
- **archive** — Moves resolved Work Log entries into the archive file
- **update (hub session)** — Pulls the public toolkit repo's latest into the hub on this host, trust-review gated. A consumer on this host sees changes to imported hub files when it begins a new session. A consumer on another host sees such changes when it begins a new session after its host's hub has updated.
- **propose upstream** — Sends a local toolkit fix to the public repo via fork+PR
- **update consumers** — Writes changes into each registered consumer's own project files and its registry entry so they match what the hub now offers. A change to a hub file a consumer already reads is live for it and needs no run. It does not carry shared-resources entries.
- **new tool** — Adds a new tool to the shared library, public (`toolkit\`) or private (`toolkit_private\`, kept on this machine); asks which first, and `new private tool` skips the question. A consumer gets the tool only by opting in through `update` or `update consumers`, and the public/private choice decides who else can see the code, nothing more.
- **modify tool** — Changes or removes an existing shared tool. A change to the tool's own files is live for every consumer already opted in; a change to its opt-in snippet, or removal of its hook script, needs `update consumers`.
- **self hooks** — Toggles a tool on/off for this hub's own self-use. Asymmetric parallel: a consumer project has the same "what's turned on for me" question, but it's answered by `commands`, not by a dedicated consumer-side node of its own.
- **connect project** — Registers a new (scaffold), existing hand-copied (adopted in place), or already-registered-elsewhere (host-merge) consumer
- **disconnect project** — Reverses connect_project for one consumer: this machine only, every other machine, or everywhere. Cleans up the consumer's own local @import/hook/skill references when the host being removed is this machine; a different host can only be cleaned on the registry side from here.
- **migrate consumer to reference-indirection** — One-time conversion of an already-connected host from the old direct-baked-path form to the pointer-indirection form connect_project already gives a brand-new connection for free. Every other host already connected to the same consumer picks it up automatically on its own next relocate.py/resume pass.
- **remove / uninstall** — Reverses setup_machine for this whole machine: disconnects every consumer connected here, clears this machine's own config.local.json/self-use state, and removes the origin remote from both repos, so a later setup_machine run here starts genuinely clean. Like "Safely Remove Hardware": makes the folders safe to delete but never deletes them or any of your work. Warns first that anything not committed and pushed will exist only on this disk, and waits for "proceed" or "checkpoint".
- **implicit, "resume" scan / "process requests"** — Works the change-request inbox (`change_requests\`), where consumers file symptoms because they cannot edit shared tools. `ticket_scan.py` sorts every OPEN ticket by the last line of its round-trip log: untouched or "still fails" is the hub's turn, "awaiting verify" or an open automation PR is skipped, and an unrecognized log is read by hand. For a ticket in the hub's turn, the agent treats the proposed fix as a suggestion: it checks the effect on every registered consumer, applies the fix or a better one, runs the golden suite, logs it, and leaves the ticket OPEN with the fix uncommitted until `checkpoint`. A ticket closes only when the filing consumer logs "verified PASS" (which `ticket_scan.py --mark-done` then flips when you ask) or you give an operator override. Registration tickets skip this round-trip: the agent adds a note to the consumer's registry entry, then closes the ticket.
- **read setup_machine.md and follow it** — Configures this machine's copy of the hub, checking and asking at each step instead of guessing. First detects the folder's shape (already nested outer + `toolkit\`, a flat toolkit clone, or unclear) and asks whether this hub already has a remote; a flat clone is nested and then given a new outer scaffold or attached to the existing remote. Then it confirms Python 3 and git, picks a `host_id` (offering names already used on this hub), and proposes identity from git config and the outer remote. The complete `config.local.json` is shown for your go-ahead before it is written. After that it adds the routine-command Bash allowlist, turns on the default self-use tools, runs `relocate` and the golden suite, and registers this host in any shared-resources entries. Needs the hub under your home directory; runs once per machine, and `remove / uninstall` is its reverse.
- **relocate (run after a hub move or rename)** — Brings every consumer registered on this host back in line with where the hub now lives, via `relocate.py` (`--dry-run` previews, `--consumer <slug>` scopes to one). For each consumer it pulls that consumer's repo, then rewrites only the Tower-Crane-owned parts: the hub import lines, the skill stubs, the hub pointer and dispatch wrapper (only where the consumer already has them), and the command of each opted-in hook in its `.claude\settings.json`, leaving unrelated settings alone. Unlike most hub commands it then commits and pushes in the consumer's own repo, so its next session needs only to confirm the hooks still fire. Consumers not connected on this host are skipped, and a run on an already-current consumer changes nothing. Other hosts need no run of their own: they pick the change up at their next relocate or `resume` pass. `setup_machine` and `update` run it, and a `[NOTICE]` from any script after a hub move points to it.
- **read setup_automation.md and follow it** — Turns on an hourly, unattended pass on this machine, off by default and inert until the final switch. It confirms the headless `claude` CLI resolves, walks you through the `automation` block in `config.local.json` (cadence, tickets per tick, attempts before a stuck ticket backs off), and schedules `run_automation.py` with Windows Task Scheduler (cron and launchd are documented, not yet used). Only then does it flip `automation.enabled` to true, with your go-ahead, and check a `--dry-run` tick by hand. Each tick refreshes compliance guidance at no AI cost and applies at most one fix-worthy ticket directly, with no PR or branch: the fix is committed locally in `toolkit\`, unpushed, and the ticket's round-trip log line is pushed to the outer repo. It never flips a ticket to DONE, never pulls `toolkit\`'s `origin`, and only reports when an update is available. It pauses while the machine is locked or logged out.
- **(no standalone trigger — reached only via curate_shared_resources step 3)** — Writes one hand-authored guidance file into every (or one) registered consumer's COMPLIANCE_GUIDANCE.md, and is reached only through `curate shared resources`.
- **curate shared resources** — Writes a one-line pointer for each chosen shared-resources entry into every registered consumer's `COMPLIANCE_GUIDANCE.md` `## Broadcast` section, never the entry's content. A consumer sees it at its next resume check.
- **register host** — Proactively registers this machine into every shared_resources catalog entry it's missing from — bringing this machine's registrations up to parity with what's already registered on other machines — so an entry's Hosts: block stays accurate everywhere instead of drifting silently. The catalog-wide counterpart to apply's own per-adoption [HOST-GAP] check. Also runs automatically as setup_machine.md's Step 8a for a newly connected machine.
- **commands / new-operator signals** — Meta/index — the full flat cheat sheet, hub side
