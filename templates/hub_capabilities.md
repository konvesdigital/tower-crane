## Hub commands and what each one does

- **checkpoint** — Saves progress, commits, pushes — scoped to whichever project the session is in
- **resume / quick resume** — Pulls latest, checks compliance/tickets, picks up where left off. "quick resume" is the identical capability run in a faster mode right after a checkpoint, skipping sync checks — not a separate capability, just a lighter mode of this same one.
- **archive** — Moves resolved Work Log entries into the archive file
- **update (hub session)** — Pulls the public toolkit repo's latest into the hub, trust-review gated
- **propose upstream** — Sends a local toolkit fix to the public repo via fork+PR
- **update consumers** — Writes changes into each registered consumer's own project files and its registry entry so they match what the hub now offers. A change to a hub file a consumer already reads is live for it and needs no run. It does not carry shared-resources entries.
- **new tool** — Adds a new tool to the shared library, public (`toolkit\`) or private (`toolkit_private\`, kept on this machine); asks which first, and `new private tool` skips the question. A consumer gets the tool only by opting in through `update` or `update consumers`, and the public/private choice decides who else can see the code, nothing more.
- **modify tool** — Changes or removes an existing shared tool. A change to the tool's own files is live for every consumer already opted in; a change to its opt-in snippet, or removal of its hook script, needs `update consumers`.
- **self hooks** — Toggles a tool on/off for this hub's own self-use. Asymmetric parallel: a consumer project has the same "what's turned on for me" question, but it's answered by `commands`, not by a dedicated consumer-side node of its own.
- **connect project** — Registers a new (scaffold), existing hand-copied (adopted in place), or already-registered-elsewhere (host-merge) consumer
- **disconnect project** — Reverses connect_project for one consumer: this machine only, every other machine, or everywhere. Cleans up the consumer's own local @import/hook/skill references when the host being removed is this machine; a different host can only be cleaned on the registry side from here.
- **migrate consumer to reference-indirection** — One-time conversion of an already-connected host from the old direct-baked-path form to the pointer-indirection form connect_project already gives a brand-new connection for free. Every other host already connected to the same consumer picks it up automatically on its own next relocate.py/resume pass.
- **remove / uninstall** — Reverses setup_machine for this whole machine: disconnects every consumer connected here, clears this machine's own config.local.json/self-use state, and removes the origin remote from both repos, so a later setup_machine run here starts genuinely clean. Like "Safely Remove Hardware": makes the folders safe to delete but never deletes them or any of your work. Warns first that anything not committed and pushed will exist only on this disk, and waits for "proceed" or "checkpoint".
- **implicit, "resume" scan / "process requests"** — Applies a fix for a filed change-request ticket
- **read setup_machine.md and follow it** — One-time machine/location config bootstrap
- **(auto, after config.local.json changes)** — Regenerates consumer hook commands after the hub moves/renames
- **read setup_automation.md and follow it** — Wires up unattended ticket processing
- **(no standalone trigger — reached only via curate_shared_resources step 3)** — Writes one hand-authored guidance file into every (or one) registered consumer's COMPLIANCE_GUIDANCE.md, and is reached only through `curate shared resources`.
- **curate shared resources** — Writes a one-line pointer for each chosen shared-resources entry into every registered consumer's `COMPLIANCE_GUIDANCE.md` `## Broadcast` section, never the entry's content. A consumer sees it at its next resume check.
- **register host** — Proactively registers this machine into every shared_resources catalog entry it's missing from — bringing this machine's registrations up to parity with what's already registered on other machines — so an entry's Hosts: block stays accurate everywhere instead of drifting silently. The catalog-wide counterpart to apply's own per-adoption [HOST-GAP] check. Also runs automatically as setup_machine.md's Step 8a for a newly connected machine.
- **commands / new-operator signals** — Meta/index — the full flat cheat sheet, hub side
